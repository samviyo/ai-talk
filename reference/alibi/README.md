# Organiser reference: The Agent's Alibi

The organiser's reference scorers, runnable through the same harness the teams
use. The loader dir is overridable by env `ALIBI_TEAM_EVALS_DIR` or the
`--team-evals-dir` flag:

```
uv run python -m alibi.checks --team-evals-dir reference/alibi
ALIBI_TEAM_EVALS_DIR=reference/alibi uv run python -m alibi.evals --bot alibi.bots.naive:audit
```

Tests: `uv run pytest reference/alibi -q`.

Organiser-only: `scorer_check_notes.jsonl` here is committed, hand-maintained
organiser data (per-row rationale for `alibi/datasets/scorer_checks.jsonl`); it is
not regenerated by `alibi.fixtures` and teams never see it.

## Held-out reveal

Held-out rows are never committed: they are generated in memory from the seed
in env `ALIBI_HELDOUT_SEED`, an integer the organiser announces at the reveal.
`make reveal-alibi` runs the team suite dev vs held-out, then this reference
suite on the held-out split, and fails if either is red:

```
ALIBI_HELDOUT_SEED=<announced> make reveal-alibi ALIBI_BOT=<bot>
```

## Zig migration (Part 1 hand-off)

`zig_port/` is a full Zig port of check-alibi with these reference scorers, so the
tooling can be proven end to end: `uv run pytest reference/alibi/zig_port -q` (needs
`make zig`). `zig_port/fake_port.py` (`make fake-port`) builds a lookup-table "port" from
`alibi/golden/`: it passes `make parity` and fails `make reveal-parity`, which is the
reveal's point.

Known quirk: `score_receipts_correct` returns 0.0 when every claim is `unknown` (nothing
is gradable), so a perfect answer on such a row fails its gate. Ports reproduce it.

Limit: the hook stops agent edits, not what the team's binary does when it runs. A port
could rewrite `alibi/checks.py` or the goldens itself. The reveal trusts only the Python
tool, so before it check `git diff main -- alibi/*.py alibi/migrate` is empty.
